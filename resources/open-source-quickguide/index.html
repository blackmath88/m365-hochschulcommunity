01 / Quickguide

Open Source beginnt nicht mit GitHub

Code zu veröffentlichen ist der einfache Teil. Ein tragfähiges Projekt braucht mindestens sechs geklärte Dimensionen:

  • Lizenz Welche Nutzung ist erlaubt?
  • Ownership Wer trägt die Verantwortung?
  • Contribution Wie können andere beitragen?
  • Governance Wer entscheidet worüber?
  • Maintenance Wer hält das Projekt verlässlich?
  • Finanzierung Wie wird Arbeit ermöglicht?

Die Open Source Guides nennen README, LICENSE, CONTRIBUTING und Code of Conduct als Grundlagen. Zuständigkeiten sollten früh sichtbar sein.

02 / Quickguide

Erst klären, was «offen» bedeuten soll

Open Source

Öffentlicher Code mit einer OSI-konformen Lizenz. Breite Wiederverwendung und Beiträge sind möglich.

Community Source / InnerSource

Zusammenarbeit in einem definierten institutionellen Netzwerk; ein möglicher Rahmen, solange Rechts-, Sicherheits- oder Vertrauensfragen offen sind.

Die Begriffe sind nicht identisch: Community Source kann offen lizenziert sein; InnerSource beschreibt offene Arbeitsweisen innerhalb einer Organisation.

Proprietär + Kooperation

Die Kontrolle bleibt bei einer Institution oder einem Anbieter. Andere beteiligen sich über Vereinbarungen oder Services.

Open Source ist eine Governance-Entscheidung – nicht nur eine Lizenzentscheidung.

03 / Quickguide

Wer entscheidet?

Die Open Source Guides beschreiben drei häufige Muster. Keines passt automatisch zu jedem Projekt.

BDFL / Lead Maintainer

Eine Person hat das letzte Wort: schnell und klar. Risiko: Abhängigkeit von wenigen Personen.

Meritocracy

Einfluss wächst durch Beiträge. Risiko: schwieriger Einstieg und informelle Hierarchien.

Consensus / Liberal Contribution

Aktive Maintainer suchen Konsens. Das kann föderierte Zusammenarbeit unterstützen; Entscheidungen können länger dauern.

Hat eine Institution eine Stimme – oder eine Person?

Institutionen können Sponsoren oder Mitglieder sein. Maintainer-Verantwortung liegt üblicherweise bei konkreten Menschen. Mitgliedschaft, Finanzierung und technische Entscheidungsrechte sollten deshalb getrennt beschrieben werden.

05 / Quickguide

Geteilte Verantwortung technisch absichern

Ein pragmatisches GitHub-Setup macht Verantwortlichkeiten überprüfbar:

  • Neutrale GitHub-Organisation mit mindestens zwei Owners, möglichst aus verschiedenen Institutionen
  • Externe Anbieter als Outside Collaborators mit passenden Zugriffsrechten
  • Pull Requests statt direkter Änderungen am Hauptbranch; Branch Protection / Rulesets
  • CODEOWNERS und ein zweites Review für sicherheitskritische Bereiche
  • Private Vulnerability Reporting als vertraulicher Meldeweg
  • CONTRIBUTING, CODE_OF_CONDUCT und SECURITY mit erreichbaren Ansprechpartnern

Bei einem M365-Governance-Tool besonders wichtig: Permissions, Graph-Zugriff und Tenant-Privilegien.

06 / Quickguide

Beiträge sind mehr als Code

  • Testen
  • Dokumentieren
  • Reviewen
  • Entwickeln
  • Product-Arbeit
  • Finanzieren
  • Services beziehen

Nicht jede Institution braucht dasselbe Beitragsmodell. Zeit, Wissen, Geld und professionelle Leistungen können sich ergänzen. Auch kleine Beiträge brauchen einen verständlichen Einstieg und eine Rückmeldung.

07 / Quickguide

Was scheint zu funktionieren?

Apereo

Eine neutrale Stiftung für Open Source im Hochschulbereich unterstützt Projekte mit Infrastruktur, Governance und Services.

Lernpunkt: Ein neutraler Träger kann Projekte unterstützen, ohne alle Entwicklung selbst zu übernehmen.

Apereo Foundation

Opencast

Aus Hochschulzusammenarbeit entstanden, 2016 Apereo beigetreten. Im Dezember 2025 kündigte das Projekt Gespräche mit Linux Foundation Europe über eine künftige Trägerschaft an.

Lernpunkt: Eine Trägerstruktur kann sich verändern, während Projekt und Community weiterarbeiten. Die Ankündigung belegt noch keinen abgeschlossenen Wechsel.

Opencast · Apereo Update

Schweizer öffentlicher Sektor / EMBAG

Die Bundeskanzlei behandelt Konsumation, Kontribution und Kreation von Open Source als Aufgaben der Bundesverwaltung.

Lernpunkt: Lizenzierung, Community, Beschaffung und Wiederverwendung sind organisatorische Fragen, nicht nur technische.

08 / Quickguide

Was kann schiefgehen?

Kuali als Diskussionsbeispiel

Kuali begann als Community-Source-Projekt. Ab 2014 übernahm eine kommerzielle Gesellschaft wesentliche Entwicklungsaufgaben. Die damalige Debatte enthielt Kritik an Transparenz und Einbezug der Community; die Stiftung begründete den Schritt mit einer tragfähigeren Weiterentwicklung.

Kuali · eigene Geschichte · e-Literate · zeitgenössische Einordnung (2014)

Ownership, Entscheidungsrechte und Ausstiegsmöglichkeiten klären, bevor viele Institutionen erheblich Geld oder Arbeit investieren.

  • Maintainer-Burnout
  • Club-Effekt / informelle Entscheidungsmacht
  • Unklare Lizenz- und Nutzungsrechte
  • Eine reine Feature-Wunschliste ohne Kapazität
  • Lokale Forks, die auseinanderlaufen
  • Zu früh zu viel Governance

09 / Quickguide

So klein kann man anfangen

Vor der Veröffentlichung

  • Bestehende Rechte am Code klären
  • Open Source vs. Community Source entscheiden
  • Lizenz rechtlich prüfen
  • README · LICENSE · CONTRIBUTING
  • CODE_OF_CONDUCT · SECURITY

Für die Zusammenarbeit

  • Neutraler Repository-Ort
  • Mindestens zwei Owners
  • Maintainer benennen
  • Merge- und Review-Regeln
  • CODEOWNERS für kritische Bereiche
  • Kommunikationskanal

In den ersten Monaten

  • Einige reale Nutzer gewinnen
  • Beitragswege ausprobieren
  • Umfang klein halten
  • Wartungsaufwand beobachten
  • Maintainer-Zeit sichtbar machen
  • Entscheidungen dokumentieren

Erst später verstetigen

  • Dauerhafte Product Ownership
  • Finanzierung
  • Trägerorganisation
  • Servicemodell
  • Formale Governance

Die Arbeitsfähigkeit zu Beginn muss trotzdem geklärt sein.

Open Source braucht nicht zuerst eine Organisation.
Es braucht zuerst ein Projekt, das andere wirklich mittragen wollen.
